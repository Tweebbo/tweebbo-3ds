# Original room and game ports

For the shared language import, selector, fonts and reception rules, read `../../Tweebbo-games-candidate-20261025/docs/games-expansion/LANGUAGES.md`. Generate native dictionaries and fonts from the same reviewed web overrides before packaging any of the three consoles.

2026-10-25 candidate scope: Nintendo 3DS, Switch and Vita. Nintendo DS is explicitly deferred. These changes are unpublished; hardware acceptance remains separate from emulator and host tests.

## Source of truth

The production candidate is `../../Tweebbo-games-candidate-20261025`, based on the current `prod-20261023-builders` hotel. Read its `docs/games-expansion/PRODUCTION-AND-CONSOLES.md` before merging or releasing. The older FastFood PoC is an art/game reference, not a replacement production tree.

Set `TWEEBBO_WEB` to the reviewed web source when rebuilding. The new Fast Food, Battle Ball and audio exporters accept this variable; their current local fallback is the dated candidate. For a future release always set it explicitly. Snow's existing exporter must use the same source and contract.

## Adding another original room

1. Extend the web `tools/game-lobby-sources.json` with the stable slug, model, recovered Director cast and explicit palettes. Run `tools/import-game-lobbies.py`. Keep registration points, depth, layer animation, collision, seats, door and original height units.
2. The importer emits web/server room data and `client/public/public-rooms/ports.json`. Keep ink 8 border matte distinct from ink 36 white removal. Preserve additive lights; a furniture palette is resolved from its original cast, not a guessed global color offset.
3. Merge only the new rooms into the current production source. Never regenerate the whole production hotel from the PoC. Preserve old room slugs, fixed furniture IDs, F3 reception layouts, checkpoints and revision conversions.
4. Export the existing modern native baseline first, then run the candidate's `python3 tools/export-game-rooms.py --export ../Tweebbo-3DS/build/export`. It selectively merges manifest rooms, preserves unrelated rooms and records SHA-256 evidence.
5. Run `python3 tools/pack.py build/export`. The manifest feeds `tools/pack-game-rooms.py`; do not edit `source/gen/`. Keep the four-page scene limit. Battle Ball Lobby and Snow Storm Lobby each occupy one 1024-square page. `heightUnit=32` is used in offline navigation and seating.
6. Refresh Switch and Vita with their respective `tools/fetch-assets.sh` workflows. Their common `source/` must remain byte-identical except the `nx/` and `vita/` backends. Packers must break equal-height sprite ties by name so Python hash randomization cannot change native coordinates between runs.
7. Check original composition, additive lights, entrance, walking, seats and room return on browser and native clients. Geometry changes to an existing room require revision/recovery tests, never deletion of stored rooms.

New activity rooms are ordinary official rooms, owner zero. They must not enter `server/src/navigator-rooms.json`: production keeps exactly the regional reception, Casino and After Hours featured, selected before the database limit. A matching private title never grants priority.

## Game-specific budgets and transport

| Game | Simulation / authority | Resident native textures | QuickJS cap |
| --- | --- | --- | --- |
| Fast Food | Original engine for practice; authenticated JSON `/ws/fastfood` authority online | One 1024-square RGBA page, 4 MiB | 4 MiB |
| Battle Ball | Authoritative hotel ACTIVITY packets; original camera, animation and tile reveal | One selected arena page, 4 MiB; five banks on disk | 4 MiB |
| Snow Storm | Original integer lockstep, 180 ms turns and 60 ms subturns | Existing bounded Snow atlas | 12 MiB |

Fast Food uses a separate bounded network queue and the same admitted hotel identity. Room networking continues while games cover the room. Snow's rules/data hash is generated by the web `tools/build-game-contracts.mjs`; mismatches must reject play, not silently desynchronize. Preserve the QuickJS `-fwrapv -fno-strict-aliasing` build flags and deterministic tests.

`tools/pack-fastfood.py`, `tools/pack-battle.py` and `tools/pack-game-audio.py` generate manifests and C data. The audio bank is capped at 4 MiB and one sample at 1 MiB; only the active game's bank is resident. Game channels 0-7 do not replace Trax channels 8-11. Atlas/page limits are build failures, not permission to allocate unbounded textures.

Fast Food now packs one-third-size source art with deterministic rectangle packing, premultiplied-alpha Lanczos reduction and extruded one-pixel borders. Bilinear sampling is limited to its atlas on each backend. Rebuild its lookup, C data and JavaScript bundle together; keep the one-page 4 MiB budget and run `tests/fastfood-atlas.py`. See `FINAL-OPTIMIZATIONS.md` for before/after evidence and download changes.

Close releases QuickJS, snapshots and audio. Texture load/free runs in update between frames. Vita must keep `vita2d_wait_rendering_done()` and every vertex-pool check. Its Battle Ball subtractive ink uses GXM fragment-program variants created during initialization and released after the render fence.

Native menus use the existing classic console controls. 3DS puts actions on the touch screen; Switch/Vita use their established button glyphs and a bottom HUD. Battle Ball's native HUD names the selected power rather than reproducing the browser's scrolling balloon column. Fast Food practice pause/replay diagnostics are still browser-only. These are explicit presentation/tooling differences, not evidence of complete feature parity.

## Validation and release boundaries

- `make -C tests` and `make -C tests online SERVER=ws://127.0.0.1:18877 WEB_BUILD=18` protect rooms, avatars, transport, identity and existing games.
- `make -C tests snow games` compares full simulations in Node and native QuickJS and exercises all verified Snow arenas and all five Battle Ball arenas/effects.
- Candidate `tests/{fastfood,battle,snow}-native-browser.mjs` exercises real browser/native transport. The Switch desktop harness uses the shared core and SDL backend, and can compile at Vita's resolution; it is not a physical Switch or Vita benchmark.
- 3DS visual steps: `tools/emu/steps-native-games` and `tools/emu/steps-games-snow`, with a LAN-only debug 3DSX.
- Vita's `TWEEBBO_GAMES_TEST` instrumentation is LAN-only, saves `out/test/games-backend.vpk` and exercises all games with the actual Vita graphics backend. It substitutes for unreliable Vita3K injected input only in that test. The final VPK must be rebuilt without this flag. The Makefile fingerprints extra compiler flags to prevent accidentally retaining the test.

Never run emulator fixtures with a public build: public builds ignore saved LAN addresses. All three test artifacts bake the private LAN target `ws://192.168.1.165:18877`. The owner-authorized 3DS debug build 79 uses the same target and is distributed only by the LAN debug updater; see `DEBUG.md`. Do not publish these artifacts as public releases or use them to test production players.

The offline navigator reads `game_room_ports` and resolves titles through the packed models; new imports must appear as ordinary public rooms there too. A 404 for a removed room returns to the current language's reception without changing identity or overriding newer navigation. See `debug-lan-79/` for regression coverage.

Physical-device frame timing, thermal/battery behavior, long-session memory and sound remain acceptance gates. This Azahar environment lacks `dspfirm.cdc`, so it cannot validate 3DS audio. Do not describe emulator frame rates as hardware results. Publishing, production migration and activation need the separate operator workflow.
